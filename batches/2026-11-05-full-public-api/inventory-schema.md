# Full public API inventory conventions

The user requests all public APIs of the thirteen exact crate versions, excluding only standard-trait implementations produced by derive. Do not equate a passing subset with complete coverage.

Use compiler rustdoc JSON for original sources, compiler-expanded source for macros and automatically_derived provenance, and original source spans for manual review. Record toolchain, target, feature configuration, source hashes and extraction commands. Default, no-default and all-features can differ; all-features alone does not establish all cfg combinations. Record mutually exclusive combinations and platform-gated APIs explicitly.

Each inventory entry should have: crate/version; stable local ID; public canonical and reexport paths; item kind; owner type including specialization/type parameters; trait including arguments; method/name/signature; defining crate/source span; cfg/features/target; origin (crate manual, macro manual, derived standard, derived nonstandard, inherited default, external blanket); safety preconditions; intended useful behavioral contract; existing theorem/evidence and its domain; coverage (proved, partial-domain, modeled boundary, unproved, tool-blocked, explicitly excluded derived-standard); remaining proof obligations and obstacle.

Keep callable entries per distinct implementation/specialization and feature condition, rather than collapsing all primitive or PRNG implementations into one name. Count public types/constants/fields/variants separately from callable bodies and describe their invariants. Track public custom trait required/default methods and each crate-supplied implementation. List inherited/default and external blanket APIs separately: their bodies belong to dependencies, not to the crate, but do not silently discard them. Downstream-created arbitrary trait implementations form an open boundary, not a finite list of bodies supplied by this crate. Document this distinction.

Only an actual derived standard trait implementation is excluded. A handwritten standard-trait implementation, macro-authored implementation, nonstandard derive (e.g. serde), and inherited defaults must not be mislabeled as derived standard. Do not count tests, proof existence, specification existence, helper assumptions, or a proof for one primitive as a proof for every public specialization.

Proofs need meaningful postconditions and actual success/error/panic/termination domains. Do not discharge an API by an impossible precondition or mere reflexivity against its own body. Explicit callbacks may have reviewed contracts; distinguish composition under callback contracts from body-proving external callbacks. Preserve actual failure evidence and source adaptations/semantic bridges.
