Overview

For ascii 1.1.0, as_byte returns the exact ASCII code for every valid AsciiChar. The eleven classification methods are correct for all 128 characters: digits are characters '0' through '9'; alphabetic is A-Z or a-z; alphanumeric additionally accepts digits; lowercase and uppercase accept a-z and A-Z respectively; hexdigit accepts 0-9, A-F or a-f. Graphic accepts byte codes 33-126 and printable accepts 32-126. Blank accepts space or tab; whitespace accepts space, tab, LF, CR and FF, rejecting vertical tab; control accepts codes 0-31 or 127. eq_ignore_ascii_case returns exactly whether the two codes are equal after mapping A-Z to a-z and leaving other codes unchanged; the independent mathematical equivalence is proved for all 128 squared valid pairs. For the AsciiChar implementation of ToAsciiChar, the checked method always returns Ok of the same value and the unchecked method returns that same value. is_ascii_punctuation accepts exactly ASCII intervals 33-47, 58-64, 91-96 and 123-126. The hand-written Default implementation returns the NUL enum value. AsAsciiStrError::valid_up_to returns its stored index; this does not establish that a separate validator found the first invalid byte. The public is_alphabetic, is_alphanumeric, is_lowercase and is_uppercase methods satisfy the same letter/digit predicates. is_whitespace accepts space, tab, LF, CR, VT and FF. For every u32 radix, is_digit returns normally at radix 0-36 and accepts exactly characters whose digit value (0-9 or case-independent A-Z values 10-35) is below the radix; other characters return false. Thus radix 0 always returns false and radix 1 accepts only character '0'. Every radix above 36 panics. The other twenty-three character/error bodies terminate normally in the model. AsciiStr::as_slice preserves the complete character sequence; as_mut_slice supplies that initial view and its generated backward function writes every valid same-length replacement back exactly. AsciiStr::len gives the exact sequence length and is_empty is equivalent to an empty sequence. For an already valid AsciiStr receiver, the AsAsciiStr checked conversion returns Ok with the unchanged view, its unchecked conversion is the same view, and the AsMutAsciiStr unchecked conversion preserves the initial view and exact same-length valid replacement writeback. These original implementations are identities, not raw byte casts or validation of other input types. AsciiString::new produces an empty sequence, len returns its exact length, and is_empty is equivalent to an empty sequence. push writes back the original sequence followed by the supplied character below the model length limit; at model length usizeMAX it fails with maximumSizeExceeded. Separately, Kani directly checked the original checked ToAsciiChar bodies for u8, i8, u16, u32 and char over their complete type domains: Ok exactly for ASCII-range inputs, preserving the codepoint, and Err otherwise. Those five body-check results are separate evidence and are not additional Lean API claims. Seven separate Kani checks also verify original case conversion and mutable writeback, as_char, case-insensitive equality and printable control pictures over all 128 valid characters (all pairs for equality). These establish A-Z/a-z mapping, exact receiver updates, ASCII code preservation and U+2400 control pictures with DEL at U+2421. For every FromAsciiError<O> with arbitrary owner type O, ascii_error returns exactly its stored AsAsciiStrError and into_source consumes the wrapper and returns exactly its stored original owner. Both terminate normally with no Clone/Copy requirement on O and no validation or conversion. The stored error index is merely projected; these methods do not establish that a separate validator found an invalid byte.

Technical limitations

Thirty-seven API mappings are Lean-proved; the other explicitly described scalar/case results are separate Kani body checks. The identity proofs for unsafe methods apply only to their original AsciiChar and AsciiStr receiver implementations, which perform no raw cast. They establish nothing about unchecked conversions from integers, char, byte slices, str or other trait implementations. The Lean mathematical code-fold is not a proof of the separate case-conversion APIs; those original bodies instead have the separately recorded full-domain Kani checks. General input validation, the remaining AsciiStr/AsciiString APIs, allocation, serde and arbitrary unsafe conversions remain unproved. The official Vec model stores only element sequences and a length bound. It does not represent capacity, Rust isizeMAX allocation limits, allocator availability, OS failure or OOM. Thus the push result and failure partition are properties of that model; no exact physical allocation/panic behavior or capacity preservation is claimed. Case conversion and printable-picture behavior have separate Kani evidence, not Lean proofs. Invalid enum representations are outside the input domain.
