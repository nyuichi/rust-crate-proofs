# proofs.rs catalogue-import daily quota

The public server source at commit `0a39304e702b196e6dff917bbf17c63dc01abcc6` limits new catalogue import jobs to **5 per authenticated user per UTC calendar day**, with a second limit of **50 per connecting-IP hash per UTC day**. This is an import-job quota, not a report-publication quota.

- [Import quotas](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/imports.ts#L749-L782): kind `import`, subject user id, limit 5; kind `import_ip`, subject SHA-256 of `CF-Connecting-IP` (user id fallback), limit 50.
- [Bucket calculation](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/core.ts#L134-L147) uses `now().slice(0,10)`, and [now](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/core.ts#L72) is `new Date().toISOString()`. This resets by switching the key at **00:00:00 UTC**, rather than 24 hours after the first request. No cleanup job is needed to obtain the new bucket.
- [Current catalogues return 200 ready, existing pending/running/retry jobs return 202](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/imports.ts#L739-L746), before quota charging. This explains why an already imported crate continues to work while a new catalogue preparation fails.
- [New jobs and quota increments share one D1 batch](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/imports.ts#L749-L782). A failed prior import does not match the early running-job query, so preparing another new job is subject to the daily quota again.
- The database [rate_limits constraint](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/migrations/0001_schema.sql#L21) is `CHECK(used<=lim)`. [core.batch](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/core.ts#L119-L125) maps that failure to HTTP 429 `daily_limit`. The error does not identify which bucket was exhausted.
- The application [Fault handler](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/worker.ts#L238-L243) returns JSON and status without setting `Retry-After`. Actual raw 429 response headers were not archived, so headers potentially added by an upstream layer were not verified.
- [Seven-day old-bucket cleanup](https://github.com/proofs-rs/proofs-rs/blob/0a39304e702b196e6dff917bbf17c63dc01abcc6/src/jobs.ts#L50-L58) is independent of the daily reset.

The saved successful ready response has server Date `Thu, 05 Nov 2026 01:17:53 GMT` (`service-limit-details.json`), and the publisher observed the 429 at approximately 01:14 UTC the same day. Under this source policy, the next bucket starts **2026-11-06 00:00:00 UTC**. It is not an exact retry-after promise: other jobs under the same user/IP could consume that bucket, and the production deployment revision was not independently identified. The observed behavior is consistent with this source.

This investigation read only the public source and existing response evidence. It did not alter production configuration, limits, account identity, or network routing. See `service-quota.json` for machine-readable provenance and uncertainty.
