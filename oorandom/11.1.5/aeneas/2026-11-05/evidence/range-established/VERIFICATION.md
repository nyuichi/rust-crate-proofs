# Established rand_range behavior — partial coverage

For oorandom 11.1.5, both `Rand32::rand_range` and `Rand64::rand_range` reject every range with `start >= end` in the extracted debug-assertion configuration. The direct original-body theorems return the Aeneas assertion-failure result, for every represented generator state.

Both methods also diverge after the public sequence `from_state((0, 0))` followed by `rand_range(0..3)`. This is a kernel-checked least-fixed-point divergence proof of the actual complete method, including its initial draw, rejection loop and final branch. Zero state and increment keep the generated word zero; width three has rejection threshold one, so no iteration accepts. The raw state pair is accepted by `from_state`; this report does not claim it is reachable from `new` or `new_inc`.

These are limited contracts for two public methods, not completed general range verification. For other valid states/ranges this packet establishes neither return bounds, termination, uniformity nor state evolution. Universal valid-input partial correctness and the first-accepted-word trace contract remain unfinished in a separate work area. Divergence is not a successful sample or a total-correctness guarantee. Rust panic payload, unwinding effects and release builds with debug assertions removed are outside these contracts.

The accompanying native observer called the unchanged public APIs: widths one and two returned zero, while width three was killed after a one-second child timeout for both widths. Those are bounded observations; the formal divergence claim relies on the Lean proof, not the timeout.

The crate source, manifest and lockfile are copied without adaptation. Official Charon and Aeneas translate the original methods and the original standard-library `u32`/`u64::wrapping_neg` bodies transparently. The narrow selector `core::num::_::wrapping_neg` avoids the pinned inherent-type name matcher's unsupported pattern; it is not a whole-standard-library include. Generated functions and types are unedited. The closure has no opaque function and uses no external wrapping-neg provider, custom translator or new standard-library model. Arithmetic, Result failure/divergence, memory representation and extraction correctness retain the usual Aeneas trusted translation/model boundary. This is not a proof of the Rust compiler or translator itself.
